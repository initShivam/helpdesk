# Implementation Plan

## Phase 0 – Foundations & Project Setup

- Initialise a Git repository and set up a main/dev branch strategy.
- Add a Docker‑Compose file that defines `web`, `db`, `redis`, `celery`, and `celery‑beat` services.
- Configure a GitHub Actions workflow that runs linting, unit tests and builds Docker images on each PR.
- Scaffold a new Django project called **helpdesk** and install Django REST Framework.
- Create a fresh React + TypeScript project (Vite) and add Tailwind CSS.
- Write a `.env.example` that documents required environment variables (DB credentials, JWT secret, Gemini API key, Gmail OAuth client, etc.).
- Add a custom `User` model that extends `AbstractUser` and run the initial migration.
 
## Phase 1 – Core Ticket Model & API

- Design a `Ticket` model with fields for status, category, subject, description, creator, assignee and timestamps.
- Add a `TicketMessage` model to store each message on a ticket, flagging whether it was generated by the AI.
- Build DRF serializers and viewsets for tickets and ticket messages, exposing standard CRUD endpoints.
- Secure the API with JWT authentication (access/refresh token flow).
- Write unit tests for all ticket endpoints, targeting at least 80 % coverage.
- Create static React pages for a ticket list and a ticket detail view using mock data.

## Phase 2 – Email Ingestion & Background Processing

- Implement a Gmail IMAP client (using `google‑auth‑oauthlib` and `imaplib`).
- Write a Celery task `fetch_emails` that polls Gmail every 5 minutes via Celery beat.
- Parse each email, create a `Ticket` and its first `TicketMessage`, and store any attachments on disk.
- Add duplicate detection based on the email `Message‑ID` and thread ID.
- Add an integration test that simulates Gmail fetching with a mocked IMAP server.
- Connect the React ticket list to the real API using React Query.
- Add a simple UI element that lets agents download attached files.

**Milestone:** Agents can view tickets that are automatically created from incoming emails.

## Phase 3 – AI Integration (RAG & Suggested Replies)

- Create a `knowledge_base` app with a `Document` model for Markdown/PDF files.
- Set up an embedding pipeline using a lightweight model (e.g., `text‑embedding‑ada‑002`) and store vectors in a `pgvector` column.
- Write a RAG service that retrieves the most relevant vectors, builds a structured prompt and calls the Gemini API.
- Add a safety filter (regex based) that removes profanity or PII before sending the prompt.
- Log each AI call in an `ai_logs` table, recording ticket, model, token usage, timestamp and the sanitized prompt.
- Create a Celery task `generate_ai_suggestion(ticket_id)` that stores the AI‑generated reply as a `TicketMessage` with `is_ai_generated=True`.
- In the UI, add a **Suggest Reply** button on the ticket detail page. While the suggestion is being generated, show a spinner. Allow the agent to either accept the suggestion (which turns it into a normal message) or edit it first.
- Write an end‑to‑end test (pytest‑django + Playwright) that covers the whole flow from email → ticket → AI suggestion.

**Milestone:** Agents can request AI‑generated responses, review them and send them to users.

## Phase 4 – Classification, Summaries & Dashboard

- Add a classification field to `Ticket` (General, Technical, Refund).
- Implement a Celery task `classify_ticket(ticket_id)` that prompts Gemini with a few‑shot example and stores the predicted category.
- Implement a summarization task `summarize_ticket(ticket_id)` that creates a concise AI‑generated summary message.
- Enhance the ticket list UI with filters for status and category, and allow sorting by creation date.
- Build a dashboard page using Recharts or Chart.js that shows:
  - Number of tickets per day
  - Average first‑reply time
  - Percentage of AI suggestions that were accepted
- Add a backend analytics endpoint (`/api/analytics/overview`) that returns the numbers needed for the charts.
- Add unit tests for the classification and summarization tasks.

**Milestone:** Full‑featured UI with filtering, AI classification, summarization and operational dashboards.

## Phase 5 – Production‑Ready Polish

- Harden JWT handling: short‑lived access tokens, refresh tokens, rotating secret and revocation endpoint.
- Add audit‑log middleware that records user actions such as logins, ticket status changes and AI suggestion acceptance.
- Implement exponential back‑off and rate‑limiting for Gemini API calls.
- Deploy a monitoring stack (Prometheus + Grafana) and expose metrics from Django (`django‑prometheus`) and Celery.
- Optimize Docker images with a multi‑stage build to keep them small.
- Write a deployment guide covering Docker Compose usage and an optional Helm chart for Kubernetes.
- Perform a security review against the OWASP Top 10 and fix any findings (CORS, CSRF, input validation, etc.).
- Run a backup and restore drill for PostgreSQL and the pgvector data.
- Finalise an end‑to‑end test suite that runs on every CI build.
- Tag a release candidate (`v1.0.0‑rc`) and obtain stakeholder sign‑off.

**Milestone:** System is ready for production launch in the chosen cloud region.
